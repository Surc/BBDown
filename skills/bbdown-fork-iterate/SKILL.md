# BBDown Fork 迭代

帮助维护 Surc/BBDown 的实际差异，并区分历史保存、当前实现和待移植内容。按用户本次目标选择审核、实现或文档工作；skill 本身不授予额外外部操作权限。

## 确定项目和基线

- 使用用户选定的 checkout 或关联仓库。先读取 `git status`、分支、提交和 remote；预期 fork 为 `https://github.com/Surc/BBDown`，直接来源为 `https://github.com/aliveranme/BBDown`，原始项目为 `https://github.com/nilaoda/BBDown`。remote 名称只作惯例，不作为仓库身份的证据。
- 若当前目录不是该项目，使用现有项目上下文定位；不要把个人工作目录或别的仓库改造成 BBDown，也不要凭历史路径找到目录后直接写入。
- 读取检出版本的 `AGENTS.md`。存在时，按需要读取 `LOCAL_CHANGES.md` 和 `docs/ITERATION.md`。它们的提交号与测试结果是带日期的记录，不能代替当前状态。
- 对比 fork 和上游时读取真实 refs，按功能识别“仍需要”“上游已覆盖”“需要重写”。历史 `fix/local-playback-decrypt-mux` 基于 v1.6.11，不能整段覆盖新版 master。

## 审核与移植

- 上游已实现同等修复时保留上游实现，检查本地回归用例是否还有补充价值。只有证据支持时才移植尚缺行为；不因文本 diff 不同而认定功能缺失。
- 整片播放状态修复应保留当前 Parser 的业务错误、风控、根节点定位和日志文本净化。验证 `PLAY_WHOLE` 不被误拒，同时真正受限、未知和错误响应继续受检查。
- legacy 回退用结构化响应决定，明确 API 范围与可重试状态，最多一次格式回退，`durl` 重请求保持格式状态。检查每轮响应、有效轨道、取消传播、文档所有权和所有退出路径的释放；不能把试看、空轨道或没有触发回退的成功下载说成完整回退成功。
- 构建、锁文件、AOT 和测试约束以当前基线为准。不要把历史的 SDK 降级带入新版，或为让检查通过而扩大异常吞噬、关闭校验、复制旧实现。
- 使用 `fix/`、`docs/` 等符合仓库约定的分支；修改 master 通过 PR。审核请求只产生结论和证据，不能自动变成实现、推送或合并请求。

## 验证与说明

- 选与改动相符的验证：代码变化使用当前项目的相关测试和必需 CI 检查；文档/skill 变化检查链接、UTF-8/LF、diff 和 skill-creator 的 `quick_validate.py`。不为文案改动新增重复测试。
- 优先用 `IApiTransport` 注入响应检查解析流程。把方法级离线复现、完整解析夹具、真实外部工具、在线接口及完整 CI 分别报告，不能相互替代。
- 记录实际命令、基线、通过/失败/未运行范围和原因。历史测试计数不可当作新版结论；ffmpeg 测试静默提前返回时不可声称真实混流已执行。
- README 和 fork 自有说明只描述本次调整及其原因、前后行为、兼容性和验证；通用功能、参数、教程链接上游。保留继承的许可证及归属声明。
- 已提交、上游已覆盖、计划中、待验证内容分开写。代码迭代后同步调整说明，旧审核若保留必须标明日期和提交。
- skill 的仓库版本位于 `skills/bbdown-fork-iterate/`；本机版本是独立副本。用户要求同步时才更新安装目录，保持资源和 UI 元数据一致。

## GitHub 交付

使用当前可用且有相应权限的 GitHub 接口或 Git 登录完成用户已授权的动作。连接器的读权限、用户的写权限与 OAuth 的权限范围分别核验，不能把它们视为相同。

认证失败时先读错误，检查是否为仓库授权或历史工作流权限；选择当前权限内可行的方法。需要登录或额外授权时说明具体原因和操作，不能要求用户把 token 粘贴进聊天。使用临时凭据时在完成或停止后清理本地文件。

不记录 Cookie、密钥、签名地址、登录文件和原始对话。推送后核对远端提交及文件范围；创建 PR 后附上 PR 并核对目标仓库和分支。用户没有要求合并或发布时，不替用户执行这两步。
